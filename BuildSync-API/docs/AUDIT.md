## Identifier conventions (critical for authorization work)

| Identifier | Meaning | Where used |
|---|---|---|
| `User._id` | Login identity for **all** roles | JWT payload, `/auth/verify`, `/leave/:id/:role`, `/work-request/:id/:role` |
| `Employee._id` | Workforce record (has `userId`, `department`, `employeeId`, `salary`) | `/employee/:id`, `/leave/:id/admin`, `/salary/:id/admin`, `/attendance` |
| `Client._id` | Client record (has `userId`) | `WorkRequest.clientId` |
| `Employee.employeeId` | Human string e.g. `EMP-1042` | `PUT /attendance/update/:employeeId` |

**The `:id/:role` convention:** when `role === "admin"` the id is an
`Employee._id`/`Client._id`; otherwise it is a `User._id` that the server
resolves. This is why the frontend must send `user.role`, and it is a
confusing surface — it is preserved for backward compatibility but is now
resolved from the **verified token**, not the caller.

## Confirmed risks

| ID | Severity | Finding | Evidence |
|---|---|---|---|
| **R0** | **Critical** | `PUT /setting/change-password` reads `userId` from the **request body**, not the token. Any authenticated user can reset any other user's password, including admins. | `client` token → `PUT` admin's password → `200`, `bcrypt.compare` confirmed the new password works. |
| **R1** | **Critical** | `routes/client.js` has **no `authMiddleware` on any route**. `POST /client/add` and `GET /client` succeed with no token. | `POST /api/client/add` (no header) → `{"success":true,"message":"Client created"}`; `GET /api/client` → full client list with emails/phones. |
| **R2** | **Critical** | `POST /work-request/add` has **no `authMiddleware`** and trusts body `userId` to establish ownership. | No token → route executes; ownership is client-supplied. |
| **R3** | **Critical** | **No server-side role authorization exists.** `authMiddlware.js` only verifies *that* a token is valid, never *what role* it holds. The entire role hierarchy lives in React Router. | `employee` token → `GET /employee` `200`, `GET /leave` `200`, `GET /salary/<other>/admin` `200`, `PUT /leave/:id` approve → `200` (stored `Approved`). |
| **R4** | High | Department delete cascade destroys employees + users + leave + salary, but **leaves `Attendance` rows orphaned**. Irreversible historical data loss. | `models/Department.js:17` `pre("deleteOne")` deletes `Employee`, `Leave`, `Salary`, `User` — not `Attendance`. |
| **R5** | High | No pagination anywhere — `GET /employee`, `/leave`, `/work-request`, `/client` return unbounded result sets. | Controllers call `.find()` with no `limit`. |
| **R6** | High | Mass assignment: `POST /employee/add` and `POST /client/add` take `role` from the body. An admin-only route lets the caller choose the role; a non-admin (per R3) can create admins. | `req.body.role` written directly into `new User({...})`. |
| **R7** | Medium | `POST /auth/forgot-password` **returns the reset token in the JSON body**. Any registered email yields a valid password-reset token. | Response body contains `resetToken`. |
| **R8** | Medium | `Attendance.status` enum is `Present|Absent|Sick|Leave`; the UI writes lowercase. It only persists because `findOneAndUpdate` skips validators. | Schema enum vs. `AttendanceHelper.jsx` `markEmployee("present", …)`. |
| **R9** | Medium | `defaultAttendance` middleware writes `staus: null` (typo for `status`). | `middleware/defaultAttendance.js`. |
| **R10** | Medium | No uniqueness on `Attendance` `{employeeId, date}` → concurrent page loads can create duplicate daily rows. `findOneAndUpdate` runs with an unfiltered insertMany. | Schema has no compound index. |
| **R11** | Medium | Auth failures return **404** instead of 401/403, and a missing `Authorization` header throws → **500**. | `authMiddlware.js` returns 404 for no token; `req.headers.authorization.split` throws when header absent. |
| **R12** | Medium | `GET /dashboard/summary` sums `Employee.salary` and labels it "Monthly Salary". That is a **configured payroll commitment**, not cash paid — no payment records exist. | `dashboardController.js` `$group {$sum: "$salary"}`. |
| **R13** | Low | `User.createAt` (typo for `createdAt`), and `updatedAt` never updates on `.save()`. | `models/User.js`. |
| **R14** | Low | No global error handler; a thrown async error in a controller returns Express's HTML page, not JSON. | `index.js`. |

## Prioritised plan

**Phase B — Security (critical)**
B1 Extract `app.js` so the app is testable without binding a port.
B2 `middleware/authenticate` (401 semantics) + `middleware/authorize` (`requireRole`, ownership helpers).
B3 Fix R0 — identity from token; add an explicitly authorized admin reset.
B4 Fix R1 — authenticate and role-split `routes/client.js`.
B5 Fix R2 — `POST /work-request/add` derives identity server-side.
B6 Apply role + ownership rules across every remaining route (R3).
B7 Fix R6 — ignore `role` in body except on the admin-only route.

**Phase C — Data integrity**
C1 Attendance: fix R9, normalise R8 with a migration, add compound unique index (R10), enable `runValidators`.
C2 Department: replace destructive cascade with archival that preserves attendance/payroll history (R4).
C3 Migration scripts, idempotent and rollback-aware.

**Phase G — Tests**
Zero-new-dependency suite on `node:test` hitting a real app instance against an isolated `_test` database. Covers the R0–R3 matrix plus leave/attendance/salary workflows.

**Deferred (documented, not silently skipped)**
- Full WorkRequest lifecycle + assignment (Phase E / §6.4) — a new domain, needs product sign-off on the state list.
- Audit trail collection (§12) — depends on the lifecycle decision above.
- Project model separate from `Department` (§6.4/§15).
